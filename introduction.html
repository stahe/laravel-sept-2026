    Ce document est un produit de l'IA Claude d'Anthropic. Il fait suite au document Introduction étape par étape au framework web [Flask] (2026), qui faisait lui-même suite aux documents Introduction étape par étape au framework web [Spring MVC], Introduction étape par étape au framework web [ASP.NET Core MVC] et Introduction étape par étape au framework web [NestJS] (2026). Le présent document transpose le cours [Flask] dans le monde [PHP] :

    • le framework [Flask] et le langage [Python] sont remplacés par le framework [Laravel] 13 et le langage [PHP] (version 8.4 ou plus récente) ;
    • les vues [Jinja2] sont remplacées par des vues [Blade], le moteur de vues de [Laravel] ;
    • la validation par [Pydantic] et [WTForms] est remplacée par celle de [Laravel] : les règles de validation, et les requêtes de formulaire ([FormRequest]) ;
    • les quelques dizaines de lignes de sécurité écrites à la main pour [Flask] sont remplacées par le système d'authentification de [Laravel] (gardes, middlewares, [Gate], façade [Hash], limiteur de tentatives), complété par la bibliothèque [firebase/php-jwt] pour les jetons JWT ;
    • l'ORM [SQLAlchemy] est remplacé par l'ORM de [Laravel], [Eloquent], toujours avec une base [MySQL].

    Le document suit exactement la progression du cours [Flask] : d'abord de nombreux petits projets, chacun centré sur une notion, puis une étude de cas complète, une application web de prise de rendez-vous pour un cabinet de médecins, dont tous les fichiers sont commentés. Les exemples portent les mêmes numéros et traitent les mêmes sujets que dans les cours [Flask], [Spring MVC] et [ASP.NET Core MVC] : un lecteur qui connaît l'un de ces cours peut comparer les frameworks exemple par exemple. Ce n'est pourtant pas nécessaire : ce document se lit seul, et ne suppose aucune connaissance de ces frameworks. On suppose seulement connues les bases de la programmation web (le protocole HTTP, le langage HTML) et celles du langage [PHP] (variables, tableaux, fonctions, classes). Le cours Introduction au langage PHP7 par l'exemple (2019) présente le langage lui-même, pour qui aurait besoin de le découvrir d'abord ; les nouveautés de [PHP] 8 utilisées ici (propriétés promues, classes [readonly], énumérations, arguments nommés, opérateur nullsafe...) sont expliquées à leur première apparition.

    1.1. La place de Laravel dans une application web

    Une application web est souvent construite en couches, chaque couche ne parlant qu'à ses voisines :

    • la couche web reçoit les requêtes HTTP du navigateur et lui renvoie des pages HTML. C'est elle que [Laravel] nous aide à écrire ;
    • la couche métier contient les règles de gestion de l'application (« un patient ne peut avoir qu'un rendez-vous à venir », par exemple). Elle ignore tout du web : elle pourrait aussi bien servir une application en ligne de commande ;
    • la couche d'accès aux données (couche DAO, pour *Data Access Object*) lit et écrit dans la base de données. Nous utiliserons [Eloquent], l'ORM (*Object Relational Mapper*) de [Laravel], qui fait correspondre les lignes des tables et des objets [PHP].

    La couche web suit elle-même le modèle MVC (*Model - View - Controller*) :

    • le contrôleur (C) est une classe [PHP] dont les méthodes, appelées actions, traitent chacune un type de requête (par exemple [GET /agenda]). Une action lit les paramètres de la requête, fait travailler la couche métier, puis choisit la vue à afficher ;
    • le modèle (M) est l'ensemble des données que l'action transmet à la vue ;
    • la vue (V) est un fichier [Blade] (extension [.blade.php]) : une page HTML qui contient des expressions [{{ ... }}] et des directives [@if], [@foreach]..., que le moteur [Blade] remplace par les données du modèle.

    Une remarque de vocabulaire, pour éviter une confusion : dans [Laravel], le mot modèle (*model*) désigne d'ordinaire un modèle [Eloquent], une classe qui représente une table de la base de données (dossier [app/Models]). Ce document emploie le mot dans ses deux sens, en précisant chaque fois lequel : le modèle de la vue (les données transmises à une vue) et le modèle [Eloquent] (à partir du chapitre sur l'accès aux données). Le mot gabarit désigne la vue commune dont les autres pages héritent (chapitre sur les vues).

    Le traitement d'une requête suit les étapes numérotées du schéma :

    • 1 : le navigateur envoie une requête HTTP, par exemple [GET /agenda?idMedecin=1&jour=2026-09-26] ;
    • 2 : le serveur web reçoit la requête et la confie à l'application [Laravel], par le fichier [public/index.php]. Pendant le développement, ce serveur est celui qu'intègre [PHP], lancé par la commande [php artisan serve] ; en production, ce sera un serveur comme [nginx] ou [Apache], associé à [PHP-FPM]. La requête traverse des middlewares, des classes qui interviennent sur toutes les requêtes (les cookies, la session, la sécurité...), puis [Laravel] compare le chemin demandé aux routes de l'application et choisit l'action chargée de cette requête : c'est le routage ;
    • 3 : l'action demande à la couche métier les données dont elle a besoin ; la couche métier s'adresse, si nécessaire, à la couche DAO, qui interroge la base [MySQL] en SQL ;
    • 4 : l'action construit le modèle M de la vue et demande au moteur [Blade] de fabriquer la page (fonction [view]) ;
    • 5 : la page HTML fabriquée par la vue est la réponse de l'action, que [Laravel] renvoie au navigateur.

    [Laravel] est, de loin, le framework web le plus utilisé du monde [PHP], devant [Symfony] (sur les composants duquel il est d'ailleurs bâti). Gratuit et libre, créé en 2011 par Taylor Otwell, il fonctionne partout où fonctionne [PHP] ([Windows], [Linux], [macOS]), et [PHP] fonctionne chez presque tous les hébergeurs web. C'est un framework complet : routage, vues, validation, session, cache, authentification, traduction, accès aux bases de données, envoi de courriels, tâches de fond... tout est fourni, et conçu pour fonctionner ensemble. C'est l'opposé du micro-framework [Flask] du cours précédent, qui laissait le développeur assembler ses propres composants : [Laravel] fait beaucoup de choses de lui-même, avec très peu de code, et l'un des objectifs de ce document est de rendre visible ce qui se passe « en coulisses ». [Laravel] sait fabriquer aussi bien des serveurs qui renvoient du JSON à un client [JavaScript] ([Angular], [React], [Vue.js], [Flutter]...) que des applications web classiques, où c'est le serveur qui fabrique les pages HTML, le navigateur se contentant de les afficher. C'est ce second usage qu'étudie ce document.

    Une particularité de [PHP] explique beaucoup de choses dans [Laravel] : l'application est reconstruite à chaque requête, puis oubliée (exemple 01). Nous y reviendrons souvent.

    1.2. Les outils utilisés

    Les exemples ont été écrits et testés avec les outils suivants (leur installation est décrite en annexe) :

    • [PHP] 8.4 (toute version 8.4 ou plus récente convient), avec les extensions [intl], [mbstring], [openssl] et [pdo_mysql] ;
    • [Composer] 2, le gestionnaire de bibliothèques de [PHP] ;
    • l'éditeur [Visual Studio Code], avec les extensions [PHP Intelephense] (l'analyse du code) et [Laravel] (les vues [Blade]) ;
    • un navigateur récent ([Chrome], [Firefox], [Edge]) ;
    • l'outil en ligne de commande [curl], qui affiche les réponses HTTP brutes (il est livré avec [Windows] 10 et 11) ;
    • le SGBD [MySQL] (ou [MariaDB]), par exemple celui de [Laragon] sous [Windows], à partir du chapitre sur l'accès aux données, et pour l'étude de cas. Sous [Windows], [Laragon] installe en une fois [PHP], [Composer] et [MySQL].

    [Laravel] et les autres bibliothèques ne font pas partie de [PHP] : [Composer] les télécharge depuis le dépôt [Packagist] lors de l'installation (il faut donc être connecté à Internet ce jour-là), et les range dans un dossier [vendor]. Chaque projet décrit ses bibliothèques dans un fichier [composer.json]. Le tableau suivant présente les principales, avec les versions utilisées :

    [laravel/framework]
    le framework : routage, middlewares, contrôleurs, vues [Blade], validation, session, cache, authentification, traduction, [Eloquent]...
    13.33.0
    [symfony/*]
    les composants de [Symfony] sur lesquels [Laravel] est bâti (requêtes et réponses HTTP, routage, console), installés avec lui
    8.1
    [nesbot/carbon]
    les dates (exemple 12), installé avec [Laravel]
    3.14.0
    [brick/math]
    les nombres décimaux exacts (exemple 06), installé avec [Laravel]
    1.0.0
    [firebase/php-jwt]
    les jetons JWT (chapitre sur l'authentification)
    7.2.0

    [Laravel] s'installe d'ordinaire en créant un projet complet, par la commande :

    1
    composer create-project laravel/laravel mon-projet

    [Composer] télécharge alors le squelette d'une application [Laravel] (une cinquantaine de fichiers et de dossiers : configuration, fournisseurs de services, migrations, tests, outils de construction du [JavaScript]...), puis ses bibliothèques, et crée une clé de chiffrement. C'est ainsi que l'on commence un vrai projet. Pour apprendre, ce squelette a un inconvénient : il contient beaucoup de fichiers dont on ne sait pas encore à quoi ils servent. Les exemples de ce document partent donc de l'autre bout : l'exemple 01 est la plus petite application [Laravel] possible, et chaque exemple n'ajoute que les fichiers dont il a besoin. L'étude de cas, à la fin, a la structure d'une application [Laravel] ordinaire.

    1.3. Exécuter l'étude de cas

    Note du réviseur : je conseille au lecteur d'exécuter immédiatement l'étude de cas comme il est indiqué dans ce qui suit. Une fois bien compris le rôle de cette application de rendez-vous, demander à son IA favorite de modifier l'application dans le sens suivant : désormais chaque médecin pourra :

    • fixer lui-même les créneaux de consultation entre deux dates. Cela lui permettra de modifier ses horaires selon ses besoins ;
    • supprimer dans l'agenda d'un jour donné certains créneaux : indisponible pour raisons personnelles par exemple ;

    La modification n'est pas simple parce qu'elle implique un changement de structure de la base de données. Demandez à l'IA de vous fournir le nouveau code de l'application et le script SQL pour créer la nouvelle base de données. Pour cela, vous aurez besoin de lui fournir le zip du projet complet ainsi que le script SQL de l'ancienne base de données.

    Par ailleurs, je n'ai pas révisé le cours produit par Claude. Il avait déjà produit des cours [NestJS], [ASP.NET Core MVC], [Spring MVC] et [Flask] parfaits. J'ai supposé qu'il en était de même pour celui-ci. Si vous butez sur un obstacle de compréhension, la solution est toujours la même : demandez à votre IA favorite de vous expliquer ce que vous ne comprenez pas. Claude, par exemple, fait ça très bien. Vous aurez peut-être besoin de lui "uploader" l'exemple que vous ne comprenez pas.

    Fin de note.

    L'étude de cas qui termine ce document est une application complète. Le lecteur voudra sans doute la voir fonctionner avant d'entrer dans le détail du framework : voici comment l'exécuter. Elle se trouve dans le dossier [rdvmedecins2-laravel], à côté du dossier [exemples] :

    1

    laravel-sept-2026/
├── exemples/

    Il faut avoir installé [PHP] (8.4 ou plus récent), [Composer], [Visual Studio Code] et [MySQL] (cf. annexes). Puis :

    • créer la base de données [dbrdvmedecins2], en exécutant le script [rdvmedecins2-laravel/database/dbrdvmedecins2.sql]. Avec [Laragon], on ouvre l'outil [HeidiSQL] (bouton Base de données), puis on exécute le script par le menu Fichier / Exécuter un fichier SQL. En ligne de commande, depuis le dossier [rdvmedecins2-laravel] :
    1
    mysql -u root < database/dbrdvmedecins2.sql
    • ouvrir le dossier [rdvmedecins2-laravel] dans [Visual Studio Code] (menu Fichier / Ouvrir le dossier), puis un terminal (menu Terminal / Nouveau terminal) ;
    • installer les bibliothèques de l'application : [Composer] lit le fichier [composer.json], télécharge [Laravel] et les autres bibliothèques, et les range dans le dossier [vendor] de l'application (quelques dizaines de secondes) :
    1
    composer install
    • vérifier la connexion à la base. L'application se connecte à [MySQL] sur [127.0.0.1], port 3306, avec l'utilisateur [root] sans mot de passe (les réglages par défaut de [Laragon]). Si votre compte [root] a un mot de passe, indiquez-le dans le fichier [.env] de l'application, à la ligne [DB_PASSWORD=] (par exemple [DB_PASSWORD=monMotDePasse]) ;
    • lancer l'application :
    1
    php artisan serve --port=8081
    • [Laravel] affiche :
    1
2
3
       INFO  Server running on [http://127.0.0.1:8081].

  Press Ctrl+C to stop the server

    Le serveur de développement écoute sur le port 8081 de l'adresse [127.0.0.1] (c'est-à-dire [localhost]). Chaque requête reçue sera signalée dans la console, ainsi que les ordres SQL qu'elle envoie à la base ;

    • ouvrir l'adresse [http://localhost:8081] dans un navigateur :

    • se connecter avec l'un des comptes de démonstration, dont le mot de passe est le login : [admin] (administrateur), [pelissier], [tatou], [dupont] (médecins), [martin], [durand], [bistrou], [german] (patients). Il faut aussi recopier les caractères de l'image, en majuscules ou en minuscules.

    Une application [PHP] ne lit pas la base à son démarrage : une erreur de connexion n'apparaît qu'à la première page qui interroge la base, c'est-à-dire à la connexion. [Laravel] affiche alors sa page de débogage, et inscrit l'erreur dans le fichier [storage/logs/laravel.log]. Avec le message [SQLSTATE[HY000] [2002] Connection refused], c'est que [MySQL] n'est pas démarré ; avec [[1045] Access denied for user 'root'@'localhost'], que le mot de passe est incorrect ; avec [[1049] Unknown database 'dbrdvmedecins2'], que le script SQL n'a pas été exécuté ; avec [could not find driver], que l'extension [pdo_mysql] de [PHP] n'est pas activée. Si la commande [php artisan serve] elle-même échoue avec le message [Failed opening required '.../vendor/autoload.php'], c'est que [composer install] n'a pas été exécuté ; avec [Failed to listen on 127.0.0.1:8081 (reason: Address already in use)], que le port 8081 est déjà occupé (par une autre version de l'application, par exemple). Le fichier [README.md] de l'application décrit d'autres cas. On arrête l'application par [Ctrl-C] dans le terminal.

    L'étude de cas, à la fin du document, présente l'utilisation de l'application, puis commente chacun de ses fichiers.

Tous les exemples ayant leurs classes dans l'espace de noms [App], l'extension peut signaler des classes « en double » : c'est sans conséquence sur l'exécution, puisque chaque exemple est exécuté seul. Pour éviter ces signalements, il suffit d'ouvrir le dossier de l'exemple lui-même.
