    5. Internationalisation

    Une application internationalisée affiche ses textes dans la langue de l'utilisateur. L'étude de cas est en français et en anglais. Le principe est simple : les vues ne contiennent plus de textes, mais des clés ([MENU.ACCUEIL]), et un dictionnaire par langue associe à chaque clé son texte. La langue choisie est mémorisée dans un cookie.

    [Laravel] possède son propre système de traduction, déjà rencontré à l'exemple 09 pour les messages de validation. Il accepte deux formes de dictionnaires, rangés dans le dossier [lang] : des fichiers [PHP], un par thème et par langue ([lang/fr/validation.php]), qui rendent un tableau de clés ; et des fichiers JSON, un par langue ([lang/fr.json]), dont chaque clé est une chaîne quelconque. Nous utilisons la seconde forme : ce sont, à la syntaxe des paramètres près, les mêmes dictionnaires que ceux des versions [ASP.NET Core MVC], [NestJS], [Spring MVC] et [Flask] de l'étude de cas, et leur format se lit et s'écrit sans outil particulier. La mise en forme des dates et des montants reste celle de l'exemple 16.

    Un dictionnaire JSON est un objet dont chaque couple associe une clé à son texte. Les clés sont regroupées par thème grâce à leur préfixe : le texte « Accueil » du menu a pour clé [MENU.ACCUEIL]. Un texte peut contenir des paramètres, écrits [:nom], remplacés au moment de la traduction. (Les dictionnaires des autres versions de l'étude de cas imbriquent les objets JSON — [{"MENU": {"ACCUEIL": "Accueil"}}] — et écrivent les paramètres [{nom}] ; ceux de [Laravel] sont « à plat », et utilisent la syntaxe [:nom].) Un oubli se voit ainsi tout de suite à l'écran.

    <?php
// app/Http/Middleware/DefinirLangue.php : la langue de chaque requête

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\App;
use Symfony\Component\HttpFoundation\Response;

class DefinirLangue
{
    // les langues gérées ; la première est la langue par défaut
    public const LANGUES = ['fr', 'en'];

    public const COOKIE = 'langue';

    // la langue du cookie [langue] si elle est gérée, le français sinon
    public function handle(Request $request, Closure $next): Response
    {
        $langue = $request->cookie(self::COOKIE);
        App::setLocale(in_array($langue, self::LANGUES, true) ? $langue : self::LANGUES[0]);
        return $next($request);
    }
}
    • lignes 14-16 : les langues gérées, et le nom du cookie : des constantes de classe publiques, accessibles depuis les autres classes ([DefinirLangue::LANGUES]) ;
    • lignes 21-22 : avant chaque action, la langue de la requête : celle du cookie [langue] s'il en existe un et qu'elle est gérée, le français sinon. [$request->cookie(nom)] rend la valeur d'un cookie envoyé par le navigateur, ou [null]. [in_array], avec [true] en troisième paramètre, compare aussi les types ([===]). [App::setLocale] (exemple 16) fixe la langue de l'application pour la requête : c'est celle qu'utilisent les traductions et les mises en forme.

// bootstrap/app.php : l'application de l'exemple 22

use App\Http\Middleware\DefinirLangue;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Support\Facades\Blade;

(require __DIR__.'/../../vendor/autoload.php')->addPsr4('App\\', __DIR__.'/../app/');

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        // la route qui sert Bootstrap (cf. exemple 15)
        then: fn () => require __DIR__.'/../../commun/bootstrap.php')
    ->withMiddleware(function (Middleware $middleware): void {
        // le cookie [langue] n'est pas chiffré : il ne contient rien de secret, et
        // le serveur n'accepte que les langues gérées
        $middleware->encryptCookies(except: [DefinirLangue::COOKIE]);
        // la langue de chaque requête : celle du cookie [langue], le français sinon
        $middleware->web(append: DefinirLangue::class);
    })
    ->withExceptions()
    ->booted(function () {
        // dans les vues : @monnaie($prix) (cf. exemple 16)
        Blade::directive('monnaie', fn (string $expression) =>
            "<?php echo e(\\App\\Aides\\Formats::monnaie($expression)); ?>");
    })
    ->create();
    • ligne 19 : par défaut, [Laravel] chiffre tous les cookies qu'il dépose, et déchiffre ceux qu'il reçoit (c'est le rôle du middleware [EncryptCookies] du groupe [web], cf. exemple 20) : l'utilisateur ne peut ni lire, ni fabriquer un cookie chiffré. Le cookie [langue] ne contient rien de secret, et le serveur n'accepte que les langues gérées : nous l'écartons du chiffrement, ce qui permet de l'observer (et de le fabriquer) avec [curl]. L'exemple suivant reviendra sur ce chiffrement ;
    • ligne 21 : le middleware de la langue, à la fin du groupe [web] (exemple 16) : il s'exécute après [EncryptCookies], et lit donc des cookies déjà déchiffrés ;
    • lignes 26-27 : la directive [@monnaie] de l'exemple 16.

    <?php
// app/Aides/Formats.php : dates et montants, formatés dans la langue de la requête (cf. exemple 16)

namespace App\Aides;

use Brick\Math\BigDecimal;
use Carbon\CarbonInterface;
use Illuminate\Support\Facades\App;
use Illuminate\Support\Number;

class Formats
{
    // un montant en euros
    public static function monnaie(BigDecimal $montant): string
    {
        return Number::currency($montant->toFloat(), in: 'EUR', locale: App::getLocale());
    }

    // une date en toutes lettres. Le format "dddd LL" : le jour de la semaine, puis la
    // date au format "long" de la langue : "mercredi 23 septembre 2026" en français,
    // "Wednesday September 23, 2026" en anglais
    public static function dateLongue(CarbonInterface $jour): string
    {
        return $jour->locale(App::getLocale())->isoFormat('dddd LL');
    }
}
    • ligne 24 : [LL] est un format localisé : chaque langue a le sien ([23 septembre 2026] en français, [September 23, 2026] en anglais), là où [D MMMM YYYY] imposerait l'ordre français à toutes les langues. [dddd] ajoute le jour de la semaine.

    <?php
// app/Http/Controllers/LangueController.php : le choix de la langue

namespace App\Http\Controllers;

use App\Http\Middleware\DefinirLangue;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;

class LangueController
{
    // GET /langue/en : mémorise le choix dans un cookie, puis revient à la page précédente
    public function changer(Request $request, string $code): RedirectResponse
    {
        abort_unless(in_array($code, DefinirLangue::LANGUES, true), 404);
        // le cookie : un an de vie (en minutes), illisible par le JavaScript de la
        // page (httpOnly), jamais envoyé avec une requête POST venue d'un autre site (sameSite)
        return redirect(self::pageDOrigine($request))
            ->withCookie(cookie(DefinirLangue::COOKIE, $code, 365 * 24 * 60, httpOnly: true, sameSite: 'lax'));
    }

    // la page d'où l'on vient (entête Referer), dont on ne garde que le chemin :
    // rediriger vers une adresse complète venue de la requête permettrait
    // d'envoyer l'utilisateur sur un autre site (faille "open redirect")
    private static function pageDOrigine(Request $request): string
    {
        // parse_url découpe une URL en ses composants (chemin, paramètres...)
        $url = parse_url($request->header('Referer', ''));
        $chemin = $url['path'] ?? '';
        // "//site.com/..." serait compris par le navigateur comme une adresse
        // sur un AUTRE site : refusé aussi
        if (! str_starts_with($chemin, '/') || str_starts_with($chemin, '//')) {
            return '/';
        }
        return isset($url['query']) ? "$chemin?{$url['query']}" : $chemin;
    }
}
    • ligne 15 : un code de langue inconnu : 404 ;
    • lignes 18-19 : l'action répond par une redirection vers la page d'où vient l'utilisateur : celui-ci retrouve sa page, dans la nouvelle langue. La réponse porte un cookie, que le navigateur renverra à chaque requête : la fonction [cookie] le fabrique, et la méthode [withCookie] l'ajoute à la réponse. Ses paramètres : le nom, la valeur, la durée de vie en minutes (un an), puis deux paramètres nommés : [httpOnly: true] le rend invisible au [JavaScript] de la page ; [sameSite: 'lax'] interdit au navigateur de l'envoyer avec une requête POST venue d'un autre site ;
    • lignes 25-36 : la page d'origine est donnée par l'entête [Referer] de la requête (l'orthographe fautive, avec un seul [r], est celle de la norme HTTP), que le navigateur remplit avec l'URL de la page qui contenait le lien. Mais cet entête vient du client, qui peut y mettre n'importe quoi. Rediriger aveuglément vers cette adresse ferait de notre application un redirecteur ouvert (*open redirect*) : un lien piégé, qui porte notre nom de domaine, pourrait envoyer l'utilisateur sur un site malveillant. On ne garde donc que le chemin et les paramètres de l'URL (la fonction [parse_url] de [PHP] la découpe en ses composants, dans un tableau associatif), et l'on refuse un chemin qui commence par [//], que le navigateur comprendrait comme l'adresse d'un autre site. [Laravel] offre aussi [redirect()->back()] (ou [back()]), qui redirige vers la page précédente mémorisée dans la session (exemple 20), et non vers l'entête [Referer] : nous l'utiliserons dans l'étude de cas.

namespace App\Http\Controllers;

use App\Models\Produit;
use Brick\Math\BigDecimal;
use Carbon\CarbonImmutable;
use Illuminate\View\View;

class PagesController
{
    public function accueil(): View
    {
        return view('pages.accueil', ['nom' => 'Marie',
            'aujourdhui' => CarbonImmutable::create(2026, 9, 23)]);
    }

    public function produits(): View
    {
        return view('pages.produits', ['produits' => [
            new Produit('Clavier', BigDecimal::of('25')),
            new Produit('Souris', BigDecimal::of('12.5')),
            new Produit('Écran', BigDecimal::of('1149')),
        ]]);
    }
}
